Views & Verbs

Two questions from the audit review: should views (list, grid, detailed, carousel) be a first-class axis that decides which book features appear where, with each surface picking a default? And can the action row collapse to one Read button plus one menu, with Locate stepping into the Read slot when nothing is readable? This explores both, exhaustively, with the challenges attached.

Short answer

Yes to views as an axis — but views decide room, not meaning. Intent still decides which verb leads.

A view is a density setting. It says how much space a book gets and therefore which slots can physically fit — not which action matters on this page. Keep the two separate and every combination becomes derivable instead of hand-configured. The concrete proposal:

  1. Four views, one component. Grid, List, Detailed, and Carousel are four renderings of the same BookCollection — a carousel is a horizontally scrolling grid with a header, nothing more. Every collection can be shown in any view; each surface picks a default and says which views it allows.
  2. Any carousel can expand. The carousel header's "See all" becomes a real control that reflows the same books into List (or Grid) in place, and only navigates when the collection is a search query worth its own page.
  3. One Access button, one Save menu. The row is Read (or Borrow / Listen / Preview / Join waitlist — a verb, drawn from a closed set) plus a single Save ▾ control that owns everything else. When no copy is readable, Find in a library takes the Access slot in a quieter style, so the slot is never empty and never a dead status.
  4. Density decides slots, intent decides emphasis. Grid gets Access only (Save behind a cover-corner control); List gets Access + Save + state line; Detailed adds inline rating and description; Carousel matches Grid. On a manage surface the two controls swap weight so the shelf leads.

The rest of this document lays out every variant considered for each of those four decisions, the challenges each one runs into, and a sequence that lands the safe parts first.

01Three axes, not one

The question "what features go where" has three independent answers, and the audit's confusion comes from letting them bleed into each other. Name them and each surface becomes a coordinate rather than a bespoke template.

Axis 1 · density

View

How much room a book gets. Decides which slots exist: is there space for a second control, a state line, a description, inline stars?

  • Grid · Carousel — cover-led, ~110px wide
  • List — one row, cover + metadata + actions
  • Detailed — description, editions strip, more metadata

User-switchable. Remembered. Never changes what a book can do, only what is visible without a click.

Axis 2 · purpose

Surface intent

What the page is for. Decides which action leads and which menu groups appear.

  • discover — search, trending, subject, home
  • manage — reading log, My Books, own lists
  • commit — book page, editions table

Declared by the template. Not user-switchable. This is the audit's option G.

Axis 3 · fact

Book & session state

What is true right now. Decides which verb the Access slot shows and which menu items are enabled.

  • lending_state — borrowable, open, waitlist, none…
  • Shelf, list membership, rating, loan
  • Signed in or not

Derived from data. Already computed today; only the labels change.

The rule that keeps them separate. A view may hide a slot; it may never change what goes in it. If Grid can only fit one button, that button is still whatever intent + state say it should be — Borrow on the home page, Currently Reading ▾ on the My Books shelf. Today's grid layout breaks this rule by hiding features with CSS while the row template still decides them.

02What exists today: two view systems that don't know about each other

The idea is not new to the codebase — it has been half-built twice, in different places, with overlapping names.

SystemWhereValuesPersistenceHow features differ
Results layout work_search.html:150 · list_books.js · reading_log.html:82 · author/view.html:167 · list/view_body.html:106 details · grid LBL cookie, 1 year, via <ol-segmented-control class="tools--layout"> Same markup; grid hides details, rating, check-in with display:none (legacy.css:1490–1550)
Carousel layout QueryCarousel.html:1 · custom_carousel.html:34 carousel · grid Template parameter only — no user control Same card template; carousel--grid wraps instead of scrolling; lazy-load only in carousel mode

So "grid" already means two different things: a wrapped row whose fat parts are hidden, and a wrapped card that was never fat. The list/row world and the carousel/card world have separate templates (SearchResultsWork vs custom_carousel_card), separate CSS, separate action rendering, and no shared notion of a collection. Unifying views is mostly the work of making these two systems one — which is also exactly what the audit's Phase 2 (extract BookActions) needs. The two efforts are the same effort.

Naming. The cookie value is details, the UI says "List". If a real Detailed view is added, the word is taken. Propose the values become grid · list · detailed and details is migrated on read.

11Where Locate goes — six variants

Locate is an access action — it gets you a copy — so it belongs in the Access family. The question is whether it may take the Access slot, and only when nothing online exists. Six answers, plus a data problem that any of them has to solve.

The data problem first. LocateButton needs an edition key (/books/OL…M/-/borrow?action=locate), and WorldcatLink needs an ISBN or OCLC number. Search results are works. That is the real reason LoanStatus falls through to Not in Library for works — not an oversight but a missing input. Fixing it means picking a representative edition per work in the row (Solr already returns edition_key, isbn, oclc arrays for the work doc), and accepting that "Find in a library" from a work row searches for an edition, not the edition. Challenge C5 covers this. Every variant below assumes it is solved.

One macro call per surface, three arguments that mean something, no booleans:

Inside, one tile template (Grid/Carousel) and one row template (List/Detailed) both call the same BookActions(book, intent, density) — which is the audit's Phase 2 component, with density replacing the six booleans and telling it whether it has a state line, a labelled Save, or a corner control.

14Challenges

Everything that makes this harder than drawing it. Grouped by kind, roughly ordered by how much they constrain the recommendation. Each names the variant it bites and the way out.

Data & caching

C1

Carousel HTML is cached; shelf state is per user Blocks C3, G3, G5

QueryCarousel renders through CacheableMacro or a lazy partial, shared across users. A Save control that shows "✓ Reading" cannot be baked in. Every carousel and every Grid tile has to hydrate its shelf/list state after load.

QueryCarousel.html:29 · custom_carousel.html:37 data-config · MyBooksDropper async_load path already used by search results

Way out: one batched request per page — GET /account/books/state?keys=OL1W,OL2W,… — returning shelf, list-membership and rating for up to ~120 works; tiles render the neutral "+" state and flip on response. The dropper's async_load is the seed of this; it currently fires per-row.

C2

Carousels have no data payload, only HTML Blocks X2

Reflowing a carousel into List in place needs the books' data (title, author, availability, ratings, counts) to render an L2 row. Today the card is server-rendered; the only client-side data is the load_more query config.

custom_carousel.html:18–37 · custom_carousel_card.html renders straight from the Solr doc

Way out (pick one): (a) embed a trimmed JSON of the docs in the carousel's data-config — cheap, but roughly doubles carousel HTML weight; (b) on expand, re-fetch the same query via /search.json with view=list and render server-side partials — no weight cost, one round-trip on expand; (c) render both tile and row markup and toggle with CSS — simplest, heaviest, and Detailed can't work this way. Recommendation: (b), because the "Show more" pager needs that endpoint anyway.

C3

Descriptions are not in the search index Blocks D1–D5

Solr work docs carry first_sentence and subjects but not description. A Detailed view over 20 search results needs 20 work fetches from the DB (or a batch get_many), and a large share of works have no description at all.

openlibrary/solr schema · works' description lives on the Infogami work object

Way out: lazy-load descriptions when Detailed is toggled on (one get_many for the visible page, rendered as a partial), and define the fallback ladder: description → first_sentence → "Subjects: …" → nothing (row collapses to L2 height). Consider indexing a 300-char description_snippet in Solr later if Detailed earns it. Never make Detailed the default until the fetch is measured.

C4

Availability is per-edition; the row is per-work Affects every view

Borrow/Read/Preview state comes from the work's "best" IA edition (lending_edition_s / ia in the doc). Detailed's editions strip (D2) will show covers whose availability differs from the row's button, prompting "which one am I borrowing?"

Way out: the strip links to the editions table; the button always acts on the lending edition; the state line may say "This edition: 1 of 3 available". Don't try to make the strip interactive.

C5

Locate needs an edition; search rows are works Blocks F1–F6

LocateButton builds /books/{edition}/-/borrow?action=locate; WorldcatLink needs ISBN/OCLC. Work docs have arrays of both, but no notion of "the representative edition for a library lookup" — and 20–30% of works have neither identifier.

LocateButton.html:3 · WorldcatLink.html:1 · LoanStatus.html:158–168 falls through to NotInLibrary when not is_edition

Way out: in the row, pick cover_edition_key if it has an ISBN/OCLC, else the first edition with one; pass it as locate_edition. Rows with no identifiers at all fall to F3 (slot empty, state line only) — measure how many; if it is large, the "Find in a library" story is weaker than it looks.

Layout & language

C6

Label width at tile density Affects G3–G5, C3, F1

"Find in a library", "Currently Reading", "Join waitlist" at ~110px in English are marginal; in German, Finnish, Tamil they overflow. Today's carousel dodges this by having only "Borrow"/"Read".

Way out: a short-form string for every verb and shelf ("Find", "Reading", "Waitlist"), chosen by density not by locale, and a tested minimum tile width (~120px) below which the tile drops the label and keeps the icon + tooltip. Both short and long forms go through i18n as separate msgids.

C7

Controls over cover art Affects G3, F6

The corner Save and the state badge sit on top of arbitrary images. Light covers wash out a light control; dark covers hide a dark one.

Way out: a fixed light chip with a subtle shadow ring (as drawn), never adaptive to the cover; and never place a control over the cover's centre. Also plan the no-cover placeholder — controls need to look right on it too.

C8

Two controls at Grid width is one too many Affects G4, R6

R6 (horizontal pair) needs ~150px; a Grid tile has ~110px. Any variant that puts two labelled buttons under a tile either truncates or wraps.

Way out: the density parameter. Below ~140px, BookActions renders G3's arrangement (one button + corner control); above, R3 stacked; above ~260px, R6 horizontal. Three breakpoints inside one component, no per-view templates.

C9

Grid currently hides features with CSS Cleanup

The existing grid layout ships the full row markup and hides rating, check-in and details with display:none. Moving to a tile template means the grid class flip becomes a re-render, not a restyle — the switcher can no longer be a pure CSS toggle.

legacy.css:1490–1550 · list_books.js:22 toggles a class only

Way out: either render both tile and row markup server-side and toggle visibility (heavy, but instant, and keeps the no-JS story), or re-fetch a partial on switch (light, one round-trip). For search results — the one surface where the switch is used a lot — rendering both is defensible; for everything else, re-fetch.

Interaction & accessibility

C10

Two switchers must feel like one system Affects S3 + S5

A toolbar segmented control on list pages and a header toggle on carousels are different widgets in different places controlling the same concept.

Way out: same icons, same order (Grid before List), same component (ol-segmented-control in a compact size), and the carousel version never persists. Document it in the design-system page.

C11

Announcing a view change and preserving focus All switchers

Re-rendering 20 rows on a view switch drops keyboard focus and tells screen readers nothing. Expanding a carousel in place inserts a large region below the reader's current position.

Way out: keep focus on the switcher; aria-live="polite" "Showing 20 results as a grid"; expanded carousel gets aria-expanded on the toggle and moves focus to the first row's title. Reduced motion: no reflow animation.

C12

Touch has no hover Kills G6, weakens C4

Any variant that reveals controls on hover has to reveal them on tap on touch, and the tap is already spoken for (navigate to the book).

Way out: don't ship hover-reveal. Controls are always rendered; density decides how compact.

C13

Split-button semantics R3, R6, G5

A split button is two buttons that look like one: the body submits a form (POST to reading log), the caret opens a menu. They need separate accessible names ("Want to Read", "More save options"), separate focus stops, and the caret needs aria-haspopup/aria-expanded — none of which today's dropper has (audit F6).

Way out: build it once on ol-button + ol-menu-popover and give it a name (ol-split-button); the results-sort control has already solved the popover half.

C14

Logged-out Save in every tile means more login interruptions G3, C3

Putting Save on every carousel cover multiplies the places an anonymous reader can hit a login wall.

Way out: the login-intent flow already exists and returns the reader to the action; measure interruption→completion. If it grates, render the corner Save on carousels only with a session, but keep it in List everywhere.

Product & scope

C15

Fourteen call sites, two template systems Cost

Unifying row and tile under one collection component touches every surface in the audit's table, across Templetor macros and Jinja, and the carousel JS (OlCarousel, lazy-load, load-more) is coupled to the current card markup.

Way out: the sequence in §15 — the collection component is introduced under the carousel first (fewest features, biggest gap), then adopted by the row shell.

C16

Detailed may not earn its keep Risk of over-building

Descriptions in results is a genuine reader benefit and also a real fetch, layout, and coverage cost. It is the least certain of the four views.

Way out: ship it as a toggle (S3), behind a flag, on search results only; promote to a first-class view if the toggle sees use. Do not build D2–D5 until D1 has numbers.

C17

Grouped rows (L6) and view are different axes Scope guard

Grouping by availability or shelf is a sort/filter concern that belongs to the results-toolbar work. If it lands as a "view", the two efforts will fight over the same control.

Way out: keep L6 out of the switcher; if wanted, it is a toolbar option ("Group by availability") that any view can honour.

16Open questions

  • Is the corner Save (G3) enough Save for a carousel, or should discover carousels get the two-button strip (G4) at the cost of a caret-only menu? Recommendation is G3; a quick prototype on the home page would settle it.
  • Should "Show descriptions" be a segment or a checkbox? Checkbox proposed (S3); if readers treat it as a distinct mode, promote it.
  • Should the expanded carousel remember itself for the session? Proposed no — but a My Books reader who always wants the Currently Reading shelf as a list has a case.
  • Where does the collapsed row for works with no identifiers land? F3 (slot empty) is the fallback; if that population is large, "Find in a library" is a smaller win than §11 implies. Needs a count.
  • Does the editions table (S12) get a Save at edition granularity? Left as the audit left it: shelving stays a work concept until there is a reason otherwise.
  • Should Grid ever be the search-results default on mobile? Two columns of G3 tiles fit a phone well and put more results above the fold; List is the safe answer, Grid the interesting one. Worth an experiment once the tile exists.
  • Buy this book in the menu on discover surfaces? Still a policy call, unchanged from the audit.
